# Data Model Foundation

Current foundational tables: `organizations`, `users`, `organization_memberships`, `services`, `clients`, `client_channel_identities`, `client_email_auth_challenges`, `client_channel_link_tokens`, `client_booking_restrictions`, `specialists`, `specialist_service_assignments`, `specialist_working_hours`, `schedule_exceptions`, `unavailable_periods`, `bookings`, `booking_events`, `content_sections`, `legal_documents`, `client_consents`, `client_onboardings`, `conversations`, `conversation_messages`, `organization_settings`, `organization_feature_flags`, `organization_credentials`, `audit_events`, Laravel session/cache/job tables, Horizon runtime data in Redis, and Laravel AI conversation tables.

M5A adds `notification_templates`, immutable `notification_template_versions`, `organization_channel_identities`, `scenario_rules`, durable `scenario_events`, `scenario_actions`, `scenario_deliveries`, and immutable `scenario_delivery_attempts`. M5B extends the generic Scenario tables with the typed `onboarding.started` event, bounded rule repeat configuration, and sequence/repeat snapshots on actions; it does not add family-specific tables. Each Scenario table is organization-owned. Composite organization/member, organization/client, organization/template, organization/rule, organization/event, and organization/action foreign keys prevent cross-organization references. Unique organization-scoped keys protect template identity, rule identity, event idempotency, action materialization, delivery idempotency, and attempt numbering. Due/status indexes support scheduler scans. `occurred_at`, `available_at`, `scheduled_for`, processing leases, and delivery instants are timezone-aware PostgreSQL timestamps; delay values are typed data converted to seconds only when scheduling.

`organization_id` owns organization memberships, services/catalog records, clients, client identities, booking-restriction history, specialists, specialist-service assignments, scheduling configuration, bookings, booking events, content sections, consents, settings, feature controls, credentials, and audit events. Membership roles are durable and explicit; legacy user ownership fields are backfilled during M1 and retained until a later safe contraction release. Composite organization/client foreign keys prevent cross-organization identity, consent, and restriction links. A specialist staff link uses a composite foreign key to `organization_memberships (organization_id, user_id)` and the application requires that membership to be active; `users.organization_id` is not consulted. Assignment rows use composite organization ownership foreign keys to both Specialists and Services, with one unique row per organization/specialist/service. Compound uniqueness/indexes include organization where identity is organization-relative.

Settings use a typed value column selected by a constrained key/type registry. Credentials use encrypted JSON casts and retain only masked output paths. Audit metadata is action-allowlisted before persistence and is not a copy of sensitive business content.

M2 onboarding records are unique per organization/client/flow version and use a composite organization/client foreign key. Conversations and messages use the same composite ownership boundary; channel/external conversation keys and provider message identifiers have organization-scoped uniqueness for deterministic idempotency.

Email authentication challenges are organization/email unique and store only a code hash, attempt count, expiry, and consumption instant. Telegram connection tokens store only a hash and bind one flow to one organization/client. Legal documents are organization-scoped, and consent evidence has a composite organization/document foreign key so a Client cannot reference another organization’s document.

Real M2/M3/M4 instants use PostgreSQL timezone-aware timestamp columns. Date-only future values use `DATE`; display formats never enter the model. Service prices are non-floating-point integer minor units paired with an explicit ISO-like three-letter currency. Specialist timezone context is optional and validated as an IANA identifier; scheduling resolves the organization timezone when it is absent, while client display timezone remains separate. Booking events are immutable lifecycle history with typed state transitions, actor, old/new values, timestamp, and allowlisted reason metadata; payment state is separate. PostgreSQL exclusion constraints block only `REQUESTED` and `CONFIRMED` booking intervals, so `PENDING_REVIEW` home-visit requests retain a preferred interval without reserving it. Booking records retain booking-specific HOME_VISIT destination/party data and typed payment handoff fields without a Location aggregate or payment ledger.

Booking creation idempotency records are organization-scoped and bound to either the authenticated staff actor or owning Client, with a request hash, optional Booking link, expiry, and a unique organization/key pair. Expired records are pruned by a scheduled command; PostgreSQL booking exclusion remains independent. NO_SHOW is a terminal Booking status, and event_version plus stable calendar_uid support immutable lifecycle/history and future calendar interoperability across reschedules.

Scenario event payloads are allowlisted snapshots of accepted domain facts rather than serialized Eloquent objects. Actions snapshot the source event, rule version and typed conditions, recipient, template, channel order, repeat plan/sequence, schedule, and a restricted render context so later template or rule edits do not rewrite already scheduled work. Delivery history stores typed outcomes and sanitized error classifications only; raw provider payloads, message bodies, secrets, and arbitrary client profiles are not persisted in Scenario audit/history projections.

PostgreSQL is authoritative. Migrations are forward-only by default and use FKs/indexes. See ADR-002, ADR-006, and the database-migrations skill.
