# Conversations

M2 provides the organization/client-scoped `conversations` and `conversation_messages` foundation. `RecordConversationMessage` normalizes channel keys, enforces the client boundary, deduplicates provider message identifiers, updates conversation timestamps, and retains only an allowlisted minimal metadata shape. Direction and author type are explicit enums so future human/AI messages share the same model.

Stage 10.2 adds `client_companion` as a logical conversation type without creating a second message store. A client Companion Conversation owns its bindings for Portal and verified Telegram transport endpoints; both transports write the same organization/client-scoped `conversation_messages` chronology. Companion messages are encrypted through the medical encryption boundary, and `RecordCompanionMessage` retains only allowlisted structural metadata. `CompanionTurn`, turn-message membership, attachment relationships, deliveries, escalations, feedback, and context epochs provide the durable execution boundary while preserving M2 records.

Companion turns are ordered under a PostgreSQL conversation lock and use tenant-scoped transport/idempotency uniqueness. A bounded pending burst or Telegram media group can assemble several independently recorded inbound messages into one AI turn; once processing starts, later messages cannot mutate it. Context assembly selects complete prior turn groups from the current epoch and always includes the current inbound group. Resetting memory increments the epoch and preserves all historical messages and runs.

The shared flow is: verified inbound event → logical Conversation/message → durable Companion turn/assembly → bounded context and permitted references → `AiWorkflowEngine` → one semantic AI message → channel delivery. Staff handoff replies are recorded in the same Conversation. See REQ-CONVERSATION-001 and the Stage 10.2 implementation candidate in `PROJECT_STATUS.md`.
