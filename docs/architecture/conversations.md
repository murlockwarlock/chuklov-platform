# Conversations

M2 provides the organization/client-scoped `conversations` and `conversation_messages` foundation. `RecordConversationMessage` normalizes channel keys, enforces the client boundary, deduplicates provider message identifiers, updates conversation timestamps, and retains only an allowlisted minimal metadata shape. Direction and author type are explicit enums so future human/AI messages share the same model.

Stage 10.2 adds `client_companion` as a logical conversation type without creating a second message store. A client Companion Conversation owns its bindings for Portal and verified Telegram transport endpoints; both transports write the same organization/client-scoped `conversation_messages` chronology. Companion messages are encrypted through the medical encryption boundary, and `RecordCompanionMessage` retains only allowlisted structural metadata. `CompanionTurn`, turn-message membership, attachment relationships, deliveries, escalations, feedback, and context epochs provide the durable execution boundary.

Legacy M2 adoption is deterministic and additive: only a non-empty, server-owned `client_id`, one organization, a `portal` or `telegram` channel, and a strict opaque `external_key` qualify. Adoption and live Companion resolution acquire the same narrow PostgreSQL ownership locks in this order: organization/client ownership, binding identity, binding row, then all relevant conversation rows in ascending primary-key order. Ownership, binding, channel, and message facts are revalidated after those locks. A qualifying source is moved into one per-client Companion conversation without copying messages; original message IDs, channels, external IDs, timestamps, direction, authors, and metadata remain intact, while legacy plaintext is encrypted in bounded batches. Missing keys, malformed identifiers, conflicting bindings, duplicate Companion targets, or ownership mismatches remain legacy and are never guessed or cross-merged. The idempotent `companion:adopt-legacy` backfill can safely be rerun.

Companion turns are ordered under a PostgreSQL conversation lock and use tenant-scoped transport/idempotency uniqueness. A text burst is pending until its text quiet window; a Telegram media group is durably `assembling`, uses a dedicated bounded album quiet window, and cannot be claimed until its persisted quiet deadline expires. A maximum assembly age and the existing item/byte limits prevent indefinite accumulation; bounds fail closed with a truthful recovery message rather than silently dropping input. The claimant rereads and seals it under the turn lock, then claims processing with a snapshot of the authoritative M10 whole-run deadline plus its bounded lease grace. A same-group item after the authoritative seal is recorded with `late_media_group_item` provenance; before finalization it fences/cancels the incomplete run and emits at most one resend notice, while after finalization it preserves the received item and explains the limitation without starting a second AI run. Context assembly selects complete prior turn groups from the current epoch and always includes the current inbound group. Previous image references are not provider inputs unless a typed, server-validated reinspection request is present. Resetting memory increments the epoch and preserves all historical messages and runs.

The shared flow is: verified inbound event → logical Conversation/message → durable Companion turn/assembly → bounded context and permitted references → `AiWorkflowEngine` → one semantic AI message → channel delivery. Staff handoff replies are recorded in the same Conversation. See REQ-CONVERSATION-001 and the Stage 10.2 implementation candidate in `PROJECT_STATUS.md`.
