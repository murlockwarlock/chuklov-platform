# Scenarios and Notifications

M5A implements the first organization-scoped scenario pipeline:

`ScenarioEvent → ScenarioRule → typed conditions → recipient → channel candidates → pinned template version → ScenarioAction → ScenarioDelivery → attempt history`.

`scenario_events` is the PostgreSQL-backed durable input boundary for scenario-relevant facts. Booking completion writes the ScenarioEvent in the same transaction as the accepted Booking mutation. `BookingEvent` remains immutable Booking business history and `AuditEvent` remains audit/security history; neither is reused as the delivery queue. Queue jobs carry only durable identifiers, while PostgreSQL row locking and state transitions protect materialization and delivery. Redis/Horizon transports and observes work but is not the correctness source.

Rules are organization-scoped, versioned on CRM mutation, and hold typed trigger, editable delay/unit, allowlisted structured conditions, recipient strategy, ordered channel priority, purpose, a pinned published template version, and an optional bounded repeat plan. Unknown condition types fail closed; arbitrary PHP, SQL, Blade execution, `eval`, and unrestricted JSON logic are not supported. M5B supports `booking.completed` and the internal `onboarding.started` event through this same rule path.

Templates have an organization/locale parent and immutable published versions. Rendering exposes only the allowlisted context variables declared by the selected version. Scheduled actions snapshot their source event, rule version and typed conditions, recipient, channel order, render context, schedule instant, and exact template version. Rule disablement remains an intentional live stop control, while later condition edits do not rewrite materialized action semantics. Deliveries have durable per-action/channel idempotency keys, attempt rows, typed delivered/retryable/permanent/unavailable/suppressed outcomes, safe fallback after retry exhaustion, and pre-delivery current-state suppression without deleting history. Stale action claims without an in-flight delivery are released for PostgreSQL rediscovery; an in-flight attempt with no persisted provider outcome remains terminally uncertain to avoid an unsafe duplicate send.

Client recipients resolve through the current organization and verified client channel identity. Internal recipients resolve only active same-organization memberships selected by explicit member IDs or roles and verified organization-member channel identities. Direct member selection is validated at CRM mutation time; role membership is resolved at materialization, then active membership and verified identity are rechecked at execution. A verified identity is not marketing consent; service/transactional purpose remains distinct from future marketing preferences. Telegram is the only established production outbound adapter in M5A/M5B; automated tests use deterministic fakes and no network token.

CRM configuration and history are organization-scoped Filament adapters. Mutations delegate to Application actions and write allowlisted audit metadata; history projections omit raw event payloads, provider payloads, secrets, and unrestricted render context.

## M5B scenario-family semantics

The post-session family is represented by ordinary editable rules on `booking.completed`. The initial seed contains RU/EN +24h, +48h, and +72h rules. The +72h seed uses only the currently supported typed `booking.status = completed` guard; the business meaning of the conditional follow-up remains an owner question (OQ-014), so no clinical or AI interpretation is implied.

Abandoned onboarding/re-engagement uses the existing internal `ClientOnboarding` progress record and `onboarding.started` event. It does not restore the removed client-facing wizard and does not create survey/test records. Rules can use typed onboarding stage/completion and explicit marketing-consent conditions, with configurable delay, bounded repeat count, repeat interval, template version, channels, and stop conditions. A missing consent record is false for the consent condition; no future communication-preference model is pulled into M5B.

Retention is also an ordinary `booking.completed` rule. The delay is the owner-configured retention window. `booking.has_qualifying_next_booking` is organization/client scoped and counts only future `requested` or `confirmed` bookings whose start is after the completed-event instant and no later than the action's configured window. `pending_review`, rejected, cancelled, completed, no-show, and past bookings do not satisfy it. The condition is evaluated when the action would be materialized and rechecked before execution, so a newly created qualifying booking suppresses an already scheduled retention action.

Repeat plans are materialized as generic `ScenarioAction` rows. A successful delivery schedules the next sequence from the actual delivery instant, preserving the action's exact condition, recipient, channel, render-context, and template snapshots. Sequence number and bounded maximum are immutable action data; rule disablement remains a live stop, and no next sequence is created after a disabled rule. Sequence-one materialization keeps the M5A idempotency-key shape for upgrade compatibility; later sequences add the sequence number.

The evaluation boundaries are explicit: rule conditions are evaluated against the event at materialization (with the configured action instant available for retention-window checks); an action re-evaluates its immutable condition snapshot and current live rule enablement at execution; template revision, recipient snapshot, channel order, render context, repeat plan, and schedule are immutable action snapshots. Template edits therefore never rewrite history.

See REQ-NOTIFY-*, REQ-CHANNEL-*, REQ-CONVERSATION-001, ADR-009, ADR-012, and ADR-004.
