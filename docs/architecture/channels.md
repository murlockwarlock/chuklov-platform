# Channels

Telegram is the first adapter through Nutgram. The `MessagingChannel` port exposes a typed capability snapshot; the Telegram adapter exposes Mini App and inline-button capabilities without leaking Telegram objects into Application/Domain workflows. Core conversation recording accepts normalized channel values and an allowlisted provider metadata shape.

The `/start` handler translates Telegram input into a localized, config-driven menu or, when an authentication/connection token is present, translates authentic bot evidence into the verified Client identity Application action. Ordinary web login uses a separate short-lived, browser-bound, single-use deep-link handshake. Mini App initData is checked in the Telegram infrastructure adapter before the client identity Application action runs. Telegram display names/usernames are never linkage evidence. Email, MAX, and Instagram remain distinct future channel identities/capability adapters; connection does not imply notification consent.

M5A keeps inbound/conversation `MessagingChannel` separate from the narrower provider-neutral outbound `NotificationChannel` port. The Scenario module supplies a `NotificationMessage` and receives typed delivery outcomes; the Telegram adapter owns Nutgram calls and returns only a safe provider reference/error classification. Ordered channel candidates and durable delivery rows are resolved by Scenario Application services, not by provider objects. Missing or unverified identities are unavailable and may fall through; retryable outcomes reuse the same delivery idempotency key and do not immediately send a duplicate. No real MAX, Instagram, email notification, or other future provider is implemented.

M11B reuses the same outbound `NotificationChannel` registry and safe template renderer. Broadcasts resolve only verified Client identities with affirmative current marketing consent, persist one stable campaign/snapshot/client message key and an immutable target/template snapshot bound to the exact draft revision, and persist a delivery-attempt claim before external I/O. Broadcast messages explicitly require a known external outcome; ordinary M5 Scenario messages retain their accepted retry behavior. Provider names, credentials, payloads, and exceptions do not enter Broadcast Domain, CRM, or audit metadata. Telegram `sendMessage` has no provider-backed idempotency contract here: a lost acknowledgement is recorded as terminal `unknown` and is never blindly replayed. Service/transactional Scenario delivery remains distinct from marketing eligibility; marketing templates are Broadcast-only. Organization-managed content and broadcast images are read as one-shot storage streams and uploaded to Telegram with multipart `InputFile`; public URLs remain a preview/external-image concern, not a prerequisite for Telegram to fetch managed files. See ADR-022.

Stage 10.2 ordinary text in a verified private Telegram chat goes directly to the shared Client Companion; `/start` and other explicit commands retain their existing handlers, while groups, supergroups, channels, and unverified users cannot invoke it. A Telegram turn owns one durable typing heartbeat owner, refreshed approximately every four seconds while the authoritative turn is processing and stopped on every terminal or handoff state.

Companion responses remain semantic conversation content. At delivery, the Telegram adapter performs deterministic Markdown/rich-text normalization, safe HTML repair, HTML-aware 4090-character chunking with formatting reopen/close state and human boundaries, then repaired-HTML/plain-text fallback on parse rejection. Chunks share one persisted semantic message; deliveries are independently leased and fenced, and actions/keyboards are attached only to the final chunk. A confirmed provider rejection may use a bounded retry; a transport error or a worker lease expiry is `uncertain`, never an automatic replay. This is an honest at-least-once boundary because the Telegram Bot API does not expose a generic exactly-once idempotency key for `sendMessage`; uncertain chunks require reconciliation rather than blind resend, and later chunks cannot overtake them. Image/photo and album input uses the same binding and turn flow; Telegram media groups are durably assembled with a dedicated bounded quiet policy and maximum assembly lifetime, sealed from authoritative locked state, and preserve deterministic item order/captions. An item arriving after seal cannot make an incomplete AI result look complete: the result is fenced or a single truthful resend notice is recorded.

See REQ-CHANNEL-*, REQ-IDENTITY-002, REQ-NOTIFY-*, ADR-004, ADR-005, ADR-009, ADR-012, and the channels/telegram skills.
