# Security Architecture

Primary controls: server-derived organization context, explicit membership roles/policies, scoped queries, private storage, secure sessions/CSRF, verified webhooks/Mini App and Telegram web auth, encrypted integration credentials, minimal queue payloads, safe logs, dependency audits, and cross-boundary tests.

M1 adds organization-scoped clients, channel identities, consents, settings, feature controls, credentials, and audit events. M2 adds a server-session client portal context, passwordless email-code authentication, verified Telegram initData signature validation through Nutgram, auth-date freshness/clock-skew checks, one-time replay protection, single-use Telegram connection tokens, browser-bound single-use Telegram web authentication, session regeneration after Client authentication, and identity resolution only through the current organization. Telegram web tokens and browser bindings are independently random and hashed at rest; authentic bot evidence selects an existing identity or creates a Client without display-name or username matching. Application actions verify current organization context and feature entitlement; UI visibility is not the authorization boundary. Email codes and Telegram tokens are hashed/not persisted in plaintext and never enter logs or audit metadata. Versioned legal documents and consent evidence are organization/document scoped with immutable published content. See REQ-SEC-*, REQ-EMAIL-001, REQ-LEGAL-001, ADR-013, and ADR-015.

M3 CRM actions keep Clients, verified channel identities, staff Users, and Specialists distinct. Client profile edits cannot replace a verified email or phone identity through the ordinary CRM form. Specialist staff links require an active same-organization `OrganizationMembership`; the composite database foreign key prevents a cross-organization link even if a legacy `users.organization_id` value is forged. Client self-service booking restrictions, specialist mutations, service/catalog mutations, and managed content mutations write allowlisted audit metadata atomically with their state changes. M3 does not create medical fields or booking/payment records.

M5A Scenario records, CRM selectors, Application actions, recipient resolution, and outbound identities are organization-scoped. Rules and templates cannot execute PHP/SQL/Blade code; template variables and conditions are allowlisted typed data. Client delivery requires a verified client channel identity, while internal delivery requires a verified identity belonging to an active same-organization membership. Scenario queue payloads contain IDs only. Durable PostgreSQL uniqueness and row locks protect event materialization, scheduled-action claiming, and recipient delivery; retryable sends retain one delivery idempotency key. CRM history exposes safe status/error classifications and omits raw event/provider payloads, message bodies, secrets, and unrestricted profile context. Service/transactional purpose is distinct from future marketing consent/preferences.

Credential values are stored with Laravel encrypted casts, replace operations update rotation metadata, and normal model/API representations are masked. Audit metadata is bounded by an action-specific allowlist before persistence. Audited M1 mutations persist their state change and audit event in one database transaction. Logging taps redact complete sensitive context and message values on every configured emitting channel, including authentication headers and exception context.

M0 repository controls deny the working tree from Docker build context except the reviewed runtime Dockerfiles, scan reachable history and the working tree for secrets, preserve an existing `APP_KEY` during repeated setup, and keep tenant/administrator fields outside ordinary User mass assignment. M2 never logs raw Telegram initData, auth headers, cookies, or identity payloads; audit metadata stores only action-allowlisted source/channel fields.

M7A implements the sensitive medical encryption and private attachment security foundations (ADR-017). Class C clinical fields (`anamnesis`, `complaints_goals`, `operations_injuries`, `medicines`, `supplements`) are encrypted at rest with AES-256-CBC and HMAC-SHA256 authenticated envelopes using `Illuminate\Encryption\Encrypter` behind `MedicalEncryptorInterface` and `MedicalKeyResolverInterface` (with an explicit `encryption_key_version` and rotation seam). Plaintext clinical fields never enter database indexes, audit metadata, queue payloads, or application logs (Monolog redaction protects medical keys). Private attachments are stored on disk `private` under UUID-based paths `medical/attachments/{organization_id}/{uuid}.{ext}`; uploads are validated with server-side MIME sniffing, explicit raw DICOM detection/rejection (magic bytes offset 128 `DICM`, MIME, and extension), 20MB limits, SHA-256 integrity checksums, and deterministic scanner/quarantine lifecycles (`pending`, `cleared`, `quarantined`, `rejected`). Downloads are restricted to `cleared` status and streamed without exposing disk paths or file storage structures. See `REQ-CLIENT-002`, `REQ-MEDICAL-SEC-001`, `REQ-ATTACHMENT-001`, `REQ-ATTACHMENT-002`, and ADR-017.
